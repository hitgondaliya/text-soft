Deep analysis (2026-09-01) of why the FR-4 font converter "doesn't work".

**Root cause:** engine (`FontConverter.cs`) is fine (42 tests pass). Only 2 mapping tables exist (`krutidev-to-unicode.json` + reverse), and the Kruti Dev font isn't even shipped (no `file`). The fonts actually bundled — `S0700810.TTF` (SHREE-DEVX-0700), `S1120810.TTF` (SHREE-GUJX-1120) — have **no** mapping table, so `FindMapping` returns null and Convert is disabled. Converter looks dead.

**Key encoding facts (measured, don't re-derive):**
- Shree-Lipi install `C:\Shree-Lipi nxt Plus`. Scheme files `*.DEV/*.GUJ/...` are 406 bytes: index = keyboard char, value = Shree **internal** glyph byte. `data/*/FLM_*.enc` = Font Layout Maps, **encrypted** (don't crack — licensed).
- `tools/KbdGen` builds a byte→Unicode "Rosetta" from `INSCRIPT.DEV` + the hand InScript layout, uses it only to emit the 156 Unicode keyboard layouts, then discards it.
- **Critical mismatch:** that scheme-derived Rosetta does NOT map the bundled `S0700810.TTF`. The redistributable TTF is ASCII-remapped (cmap 3,1 maps ~101 codes in 0x20–0xFF → Devanagari glyphs, like Kruti Dev) plus ~369 PUA conjunct glyphs. Scheme glyph-bytes (0xB0, 0xD1, …) are Shree's internal numbering and overlap the TTF's ASCII codes **0 / 101**. So keyboard-scheme data can't build the converter for the shipped font.
- Font glyph `post`-table names give no Unicode hint (ASCII glyphs unnamed). No free ground truth in the TTF.

**Implication for the plan:** to convert `S0700810`/`S1120810` we need each font's OWN byte→Unicode table (published Shree-Dev map, or hand-built + reorder rules like the SIL-derived Kruti Dev table), NOT the Shree scheme files. Confirm with client which legacy fonts actually ship for V1. See [[textsoft-brand]].

**GROUND-TRUTH SOURCE FOUND (dependency-free):** the Shree-Lipi CHM help files — `C:\Shree-Lipi nxt Plus\data\<script>\*.chm` (188 files: 40 dev, 20 guj, 28 ban, 23 tam, 22 kan, 17 tel, 16 mal, 9 ori…) and dupes in `D:\font software\Keyboard Typing Help\`. Each is a keyboard-layout help page whose HTML holds a **keystroke → Unicode** table with the char as Unicode numeric entity in the Mangal/Unicode font (e.g. `&#2309;`=अ). Extract with 7-Zip (`"C:\Program Files\7-Zip\7z.exe" x file.chm`), parse `index.htm`. This gives authoritative keystroke→Unicode per layout — use it to (a) fix the 156 shaky KbdGen-derived keyboard layouts, and (b) join with the 406-byte scheme files (keystroke→byte) to derive byte→Unicode converter tables.

**SHREE CONVERTER REVERSE-ENGINEERED (2026-09-03, licensed demo reinstalled):** The GUI converter is `TransNXT.exe` (.NET). It does NOT P/Invoke the native `CONV32.dll`; it uses its OWN embedded MANAGED assemblies. Extract them with `tools/ResX` (reads a .NET assembly's embedded manifest resources): `dotnet run --project tools/ResX -- "C:\Shree-Lipi nxt Plus\TransNXT.exe" <out>` yields `TransNXT.lib.SLConvert.dll` (algorithm), `TransNXT.lib.SLConvData.dll` (data layer), plus SLGenTools/SLTools/SLLangTool/LUtils/STL/CInst/PIkNiK. Inspect with `tools/IlPeek` (dumps types/methods/P-Invoke); decompile with `ilspycmd` (installed as dotnet global tool).
- Core API: `SLConvert.IConversion.ConvertData(ScriptID, InputLayoutID, OutputLayoutID, InputData, OpNumeralType, out OutputData, ref FontLayoutCache, ConjunctType, IsAuxiliaryFont)`. InputLayoutID = source font/layout, OutputLayoutID = target (Unicode). Recipe (from TransNXT ~line 4213): `GTFileHandlerFactory.GetFileInstance(masterEncPath,...)` + `...(layoutsEncPath,...)` → `new SLConvertWrapper(master, layouts)` → `ConvertData`. The file handlers decrypt the `.enc` internally (SLConvData uses System.Security.Cryptography).
- Data model (SLConvData `IExpoConvData`): per-script master of VFC (glyph) codes → akshar-type, "toBeKept", combine-matra, split-matra, conjuncts. Algorithm (SLConvert.Layouts.{Devnagri,Sanskrit,Oriya,...}Layout): `GetShiroreshaMatra` (reph), `Phantom1/2` (pre-base i-matra phantom), `HalantException`, `MultipleVattuException`, `Layoutcombine`. This is exactly the reph/conjunct/storage-order logic our tables still lack.
- Assemblies are obfuscated (unicode-ctrl-char class/method names) but decompile cleanly. `FontManager.exe` just installs TTFs (`GetInstallFontList`/`FontInstaller.SLFont.dll`) — no magic. Currently only S0700810/S1120810 (old 0700/1120 encoding) are installed on Windows; X-series must be installed via Font Manager.
- NEXT (oracle harness): assemble the extracted managed DLLs + point GTFileHandlerFactory at the real install `.enc` files to drive `ConvertData` as a dev-time oracle → auto-generate perfect tables. Risk: obfuscated decryption-key constants + possible licensing/init gates. Alternative: port the SLConvert algorithm + extract SLConvData tables into our own engine (shippable, no licensed DLL at runtime). GUI fallback: run TransNXT on a sample.
